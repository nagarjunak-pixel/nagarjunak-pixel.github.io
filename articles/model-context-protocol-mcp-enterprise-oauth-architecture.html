Enterprise Model Context Protocol (MCP) Architecture: OAuth 2.0 Boundaries, Least Privilege & ERP Tool Gateways

Published November 16, 2026 · Anthropic Advanced MCP Training · Lead AI Architect

The Model Context Protocol (MCP) standardizes how agent hosts discover capabilities and invoke external enterprise tools over JSON-RPC transports. However, moving MCP from local `stdio` developer laptops into enterprise cloud and ERP landscapes introduces subtle security and identity pitfalls.

1. Separating Transport Auth From Business-Layer Authorization

When prototyping FastMCP adapters against enterprise OData and REST backends (such as SAP BTP / ABAP OData, Spring Boot services, and operational CRMs), teams often conflate OAuth 2.0 token acquisition with business-layer data authorization. An OAuth 2.0 `client_credentials` grant proves machine-to-machine identity at the gateway, yet downstream ERP/ADT endpoints still enforce user-level authorization objects, business-logon contexts, and row-level scopes. Enterprise MCP servers must propagate user identity assertions (such as Okta/OAuth 2.0 on-behalf-of tokens) rather than sharing a single over-privileged service principal.

2. Four Design Rules for Production-Grade MCP Tool Servers

  • Coarse Intent Tools Over Raw SQL/OData Pass-Through: Expose bounded business actions (`get_approved_manual_revision`, `validate_part_callout`) with strict Pydantic input schemas rather than generic query strings vulnerable to prompt injection.
  • Read/Write Capability Segregation: Separate read-only discovery MCP servers from state-mutating servers, requiring fresh out-of-band human confirmation tokens on every write tool.
  • Token Caching With Clock-Skew Margin: Cache short-lived OAuth 2.0 tokens in memory with proactive refresh buffers and deterministic negative-test suites (401/403/429 handling).
  • Independent Inspector Verification: Validate every tool contract, capability negotiation, and error payload independently via MCP Inspector before wiring multi-agent orchestrators.
